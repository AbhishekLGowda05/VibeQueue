### 1. Critical Bug Fix: Realtime Table Names

**Files changed:** `frontend/src/lib/supabase.ts`, `frontend/src/components/dashboard/DashboardView.tsx`

The frontend Realtime subscriptions referenced wrong table names, meaning all live-update features (queue reordering on boost, billing triggers, ambient display updates) were silently broken against the real database.

| Location | Before | After |
|---|---|---|
| `supabase.ts` line 22 | `table: "queue"` | `table: "queue_entries"` |
| `supabase.ts` | `subscribeToAlerts()` function | Removed entirely (no `alerts` table in schema) |
| `supabase.ts` line ~82 | `table: "sessions"` | `table: "table_sessions"` |
| `DashboardView.tsx` | Imported & used `subscribeToAlerts` | Removed import and subscription |

### 3. Row-Level Security (New Alembic Migration)

**File:** `backend/alembic/versions/a1b2c3d4e5f6_rls_realtime_hardening.py`

Architecture decision: frontend Supabase client uses the **anon key** for Realtime subscriptions only. All writes go through FastAPI backend (postgres user, bypasses RLS).

- Enabled RLS on all 10 data tables (not `alembic_version`)
- Created 5 SELECT-only policies for `anon` role on Realtime tables:
  - `queue_entries`, `table_sessions`, `boosts`, `playback_commands`, `playback_events`
- Zero policies on sensitive tables (`users`, `payments`, `audit_logs`, `venues`, `songs`) — anon has no access
- Confirmed `service_role` key never referenced in any frontend file

### 4. Supabase Realtime

Same migration file adds 5 tables to the `supabase_realtime` publication:
- `queue_entries`, `table_sessions`, `boosts`, `playback_commands`, `playback_events`

NOT enabled on: `users`, `venues`, `songs`, `payments`, `audit_logs` (no reason for guests to receive changes to these).

### 5. Spend Cap Race Condition Fix

**Files:** `backend/app/core/redis.py`, `backend/app/services/queue_engine.py`

**Problem:** `queue_engine.py` lines 151-181 had a TOCTOU race — Redis GET, then check, then INCRBY as three separate operations. Two concurrent boosts from the same table could both pass the spend cap check before either incremented.

**Fix:** Atomic Lua script (`SPEND_CAP_SCRIPT`) that does check-and-increment in a single Redis `eval()` call. If cap would be exceeded, returns -1 without modifying the value. This is real money — the spend cap is ₹150/table.

### 6. Webhook Idempotency

**Files:** `backend/app/api/v1/routes/payments.py`, migration file

**Problem:** Razorpay retries webhooks at-least-once. No check for duplicate `razorpay_payment_id` meant double-processing was possible.

**Fix (two layers):**
1. Application guard: checks if payment already has `razorpay_payment_id` set before processing → returns `{"status": "already_processed"}`
2. Database guard: unique partial index `ix_payments_razorpay_payment_id` on `payments(razorpay_payment_id) WHERE razorpay_payment_id IS NOT NULL`

### 7. Production Hardening

**JWT startup guard** (`backend/app/core/events.py`):
- Refuses to boot in production mode with the dev placeholder `local-jwt-secret-key-change-in-production`
- Real 48-byte cryptographic secret generated and set in `.env`

**Rate limiting on `/sessions/join`** (`backend/app/api/v1/dependencies/rate_limit.py`, `backend/app/api/v1/routes/sessions.py`):
- 5 attempts/min/IP
- Brute-forcing 6-digit table codes now impractical (~7,200 attempts/day vs 1M keyspace)

**Error boundaries** (6 new files):
- `frontend/src/app/error.tsx` — root
- `frontend/src/app/global-error.tsx` — catches root layout errors (own `<html>`/`<body>`)
- `frontend/src/app/join/[venue]/error.tsx` — guest
- `frontend/src/app/display/[venue]/error.tsx` — ambient (auto-retries after 10s)
- `frontend/src/app/dashboard/error.tsx` — staff
- `frontend/src/app/playback/[venue]/error.tsx` — playback (auto-retries after 5s)
- All use Next.js 16 `retry` prop (not `reset` — breaking change from older versions)

**PWA manifest link** (`frontend/src/app/layout.tsx`):
- Added `manifest: "/manifest.json"` to metadata export (was missing)
